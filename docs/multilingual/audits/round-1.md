## 最初に決めたいこと

**最初の完成単位は、日本語と英語で「書く・保存する・読み返す・探す・困ったときに文章を救う」まで完結すること。**

残心の共通の軸は、紙、墨、月、余白、落ち着いて言葉を置ける感覚にする。操作説明、文字組み、読み方は各言語に合わせる。英語版でも日本語の詩を書け、日本語版でも英語の日記を書けるようにする。

今回の推奨事項は以下の7つ。

1. UIの言語設定をメモの保存データと分離する。
2. 英語対応の完成条件に、使いやすい横書きの読み返しを含める。
3. 保存失敗、復旧、削除、読み上げ、サポートまで日英の文言を揃える。
4. 言語の変更で、未保存の文章や編集中の状態を失わない。
5. 検索・件数・日付・文字の区切りを、文字列の置換とは別に設計する。
6. アプリ内UI、iOSのアプリ別言語、App Storeの掲載情報を、それぞれ検証する。
7. 日英で仕組みを完成させた後、実際の要望と翻訳を維持できる体制に合わせて、次の言語を1つずつ追加する。

この調査では、リポジトリ・アプリ・ストア設定を変更していない。進行中の実装ブランチや未公開の作業内容も確認していない。以下の「現行」は、上記mainに対する観察を指す。設計値や英語文案は提案であり、実機確認済み・母語話者校閲済みの仕様ではない。

### 小さな実関数確認で再現したこと

保存データの検査関数は、locale省略・ja・enを受理し、zh-Hant・frを受理しなかった。単に見た目の言語が合わなくなるだけでなく、保存版や復旧版を正常と判断できなくなる。

検索関数では、合成済みの「é」と「e＋結合アクセント」、合成済みの「が」と「か＋結合濁点」が一致しなかった。比較用NFC正規化で一致することを小さなNode実行で確認した。ブラウザ描画・実iPhone・VoiceOverの試験は実施していない。

## 2. 「言語」を一つの設定にまとめない

| 軸 | 例 | 推奨する扱い |
|---|---|---|
| 操作画面の言語 | 日本語 / English | アプリの表示設定 |
| 書かれた文章の言語 | 日本語の歌詞、英語の日記、混在文 | 原文の性質。UIから決めない |
| 読み返しの方向 | 縦書き / 横書き | 表示設定。本文や更新日時から独立 |
| 文章の左右方向 | LTR / RTL / 自動 | 本文・題名のレイアウト情報 |
| 地域別の表示慣習 | 日付、数値 | formatterの責務。必要な地域設定を別途保持 |
| タイムゾーン | 端末の現在地など | UI言語から推測しない |
| iOSが選んだアプリ言語 | OSのアプリ別設定 | native側の言語情報 |
| ストアの掲載言語 | 商品説明・スクリーンショット | App Store Connectで別に管理 |

例えば、以下の組合せを普通に使えることが望ましい。

- English UIで、日本語の歌詞を縦書きで読む。
- 日本語UIで、英語の長文を横書きで読む。
- English UIで、アラビア語のメモ本文を右から左へ読む。
- UIを英語に変えても、開いている日本語の文章はその位置・読み方のまま残る。

HTMLでも、言語を示すlangと、左右方向を示すdirは別の情報である。[S01][S02]

### メモデータの不変条件

言語を切り替えるだけでは、題名、本文、createdAt、updatedAt、先頭固定、復旧候補、保護中のrawデータを変更しない。

既存Note.localeは保存形式の一部として保持する。新規メモでこの値を省略する案は現行validatorと整合するが、実装時に最新コードとの照合が必要。UI言語を追加するためにNote.localeの許容値を拡張する変更は、保存形式の変更として別に扱う。

前回仕様の「updatedAtは題名・本文・印を含むメモ全体の変更時刻」「同じ固定状態内では変更の新しい順」は維持する。表示の設定変更をメモの更新として数えない。

## 3. 最初の対象言語と、その後の広げ方

### 第1段階：日本語と英語

日英を最初の完成単位とする理由は、既存の日本語体験を守りながら、横書き、文字量、単数・複数、言語選択、異常時の説明という主要な設計を一度に確かめられるため。

英語は最初の共通窓口にする。市場規模や利用者数を測定した結果として英語を推奨しているわけではない。まず完成度を揃えられる範囲を選ぶ判断である。

### 第2段階の候補

| 候補 | 翻訳以外の主要な確認点 |
|---|---|
| 繁體中文（zh-Hant） | 日本語と異なる字形・語彙、繁体向けフォント、横書きと縦書き |
| 简体中文（zh-Hans） | 簡体向け字形と語彙。繁体の機械的文字変換だけで完成扱いにしない |
| 한국어（ko） | ハングルの可読性、語間と改行、小さい画面の折返し |
| Español（es）など | 長い操作文、アクセント文字、日付表現、文法上の一致 |
| العربية（ar）など | UI全体のRTL、混在文字、フォーカス順、アイコンの方向、結合文字の描画 |

候補の順番は固定せず、利用者の声と、重要な文言を母語話者に継続確認してもらえる言語から選ぶ。翻訳未完了の言語を設定欄やストアの対応言語に並べない。

中国語のタグを将来扱う場合、単純にハイフン前だけを残してzh-Hansとzh-Hantを同一視しない。言語、文字体系、地域を区別して照合する。[S03]

## 4. 言語を選ぶ体験

### 推奨する入口

「アプリについて」または小さな設定画面に「言語 / Language」を置き、選択肢は次の3つにする。

- システム設定に従う / System default
- 日本語
- English

言語名は、その言語自身の表記にする。国旗で言語を表さない。誤って別言語を選んだあとも戻れるよう、この入口は判別しやすくする。

起動ごとに言語選択を尋ねない。初期値はsystemとし、必要な人が変更できる。ホームの静けさを保つため、普段の一覧に大きな言語切替を常設する必要はない。

### 解決する順番

1. アプリ内で明示したja/enがあれば、それを使う。
2. systemなら、iOSでは現在のアプリ言語、Webではnavigator.languagesの優先リストを使う。
3. 対応する言語がなければenを使う。

このenフォールバックは、英語の必須文言と関連ページが完成した版で採用する方針。現在の不完全な英語コピーへ即時切り替える指示ではない。

| 候補 | 日英版での結果 |
|---|---|
| ja-JP | ja |
| en-US / en-GB | en |
| fr-CA、ja-JP、en-USの順 | ja |
| fr、deの順 | en |
| 不正タグを含む | その項目を除き、残りを順に検討 |
| 不正な保存設定 | 起動を止めず、安全な既定へ戻す |

systemという設定自体を保存し、解決結果のen/jaで上書きしない。そうすることで、後からOS側の言語が変わったときも追従できる。位置情報やIPアドレスを言語推測に使う必要はない。自動選択に加え、手動選択とその保持を用意する方針はW3Cの言語選択の考え方とも整合する。[S04]

### iOSの「システム設定に従う」

nativeでは「iPhoneで設定した、このアプリの言語に従う」という意味にする。端末全体の言語とアプリ別言語は一致しない場合がある。Bundle.main.preferredLocalizationsをnativeから取得し、利用可能な辞書へ照合する案を推奨する。bridgeの実装と実機での取得結果は未確認。[S05][S06]

独自のアプリ内ja/en選択は、Web UIの表示設定である。OSのアプリ別言語を変更する機能とは区別する。コピー・ペーストなどのnativeメニューがOS側の言語で表示される組合せを実機で確認する。

より小さな実装を選ぶなら、アプリ内overrideを設けず、iOSのアプリ別言語設定だけに任せる方法もある。ただしOS設定での変更に伴うアプリ再起動を考慮し、アプリから案内する前に現在版の保存成功を確認する。保存失敗・競合待ちなら、原文の確認・取り出しと、設定へ移らず戻る導線を用意する。設定アプリへ移る経路と、アプリ内で文字列だけ変える経路を同じ保存保証として扱わない。[S05]

### 設定の保存

言語設定はメモのprimary/backup/journalとは独立させる。例としてzanshin.ui-language.v1のような名前空間を使う。

iOSで独自設定を永続化する場合は、Capacitor Preferences等の軽量設定用ストレージが候補。現状は未導入。採用時はUserDefaults利用に伴うPrivacy Manifestも確認する。設定のために既存のメモ保存方式を移行しない。[S07]

設定の読み書きが失敗しても編集は継続できるようにする。表示はメモリ上で変更し、設定画面には「設定を保存できませんでした。次回は元の言語に戻る場合があります」と伝える。メモの保存状態を成功・失敗に書き換えない。

遅い設定読込みが、利用者が選び直した言語を戻さないこと。en→jaと続けて選んだとき、遅いenの保存が最後に残らないことも契約に含める。

## 5. 縦書きと横書きを、残心の体験として両立させる

### 英語対応では横書きの読み返しを必須にする

前回の日本語初版仕様では、横書き切替を条件付きとしていた。英語を正式な対応言語にする場合は、横書きで長文を自然に読めることを完成条件へ引き上げる。

現在の縦書きは日本語の良さを伝える要素として残す。英語本文を日本語と同じ縦方向・字間に固定すると、読みやすさと世界観が競合する。CSSの縦書きでは文字体系ごとに文字の向きや混在の扱いが変わるため、同じ見た目を全言語へ押し広げない。[S08]

### 初期値と引継ぎ

- 実装中の版ですでに読書方向の選択がある場合は、その選択を最優先で引き継ぐ。
- 旧版の利用者は、これまでの縦書きから勝手に変わらないようにする。
- 新規インストール時だけ、日本語UIなら縦書き、英語UIなら横書きを初期提案にできる。
- 一度選んだあとは、UI言語を変えても読み方を変更しない。
- 文章の文字種や旧Note.localeから、自動で表示方向を切り替えない。

旧版と新規導入の識別方法は実装開始時に決める。既存の設定・移行マーカーを使い、保存データの検査を重複実行しない。メモ0件だけでは新規と判定しない。全件削除した既存利用者もいるため、初期値を決めた記録は独立して保持する。旧版利用か判定できない場合は、従来の表示を保って選択可能にする。

### 設定の置き場所

読み返し画面に、静かな「縦書き / 横書き」の操作を置く。全体の初期値とメモごとの選択を区別する場合、その記録はデバイスの表示設定に分ける。優先順位は「メモごとの明示選択 → 共通の読書設定 → 一度だけ決めた初期値」。共通設定を変えても、明示済みのメモ別選択を消さない。Note本文やupdatedAtは変更せず、設定の保存失敗も本文保存の結果と分ける。

最初の実装では、両方向の全機能を無制限に増やすより、全文、選択・コピー、拡大、読み上げ、編集から戻った位置を確実にする。横書きへ変えたのに「左へ続きます」が残るような方向依存の文言も切り替える。

### 位置の維持

UI言語だけの変更では、読んでいる位置と選択範囲を維持する。利用者が縦横を明示的に切り替えた場合は、可能なら同じ段落を見える位置にする。横スクロールのピクセル値を縦スクロールへそのまま転用しない。

## 6. 文字・余白・折返しの設計

以下は比較を始めるための基準であり、実機で確認済みの完成値ではない。

| 要素 | 日英版の設計案 |
|---|---|
| 操作UI | system sansを中心にし、ボタン・エラー・補助文を読み分けやすくする |
| 日本語本文 | 前回の明朝18pxを基点に、行間と紙の内側余白を調整する |
| 英語本文 | 読みやすい欧文serifを候補に、18px前後・line-height 1.7〜1.9・通常の字間から比較する |
| 見出し | 一般UIとブランド見出しを分け、装飾的な広い字間を本文へ一律適用しない |
| 幅 | 固定幅へ訳文を押し込まず、折返し・高さの伸長・縦積みで対応する |
| 長い単語・URL | 原文を変えず、必要な箇所で折返し可能にする。通常の英文を一文字ずつ分断しない |
| 文字拡大 | 200%でも主要操作・説明・本文末尾が欠けないことを確認する |
| コピー | 見た目の折返しや装飾がコピーされる本文へ混入しない |

日本語用のフォント指定を全言語に固定しない。CJKでは同じUnicode文字でも、言語ごとに期待される字形が異なる。本文言語が分かる場合だけ、その言語に合うフォント・langを使う。英語UIだから日本語本文まで欧文の設定に変える、という結び付け方は避ける。[S09]

将来の韓国語ではnormalとkeep-allを実データで比較する。keep-allを一律採用すると狭い領域で長い語が溢れる可能性がある。アラビア語などでは文字の連結を保ち、一文字ずつDOMへ分割したり広い字間を加えたりしない。CSSの改行・字間仕様を確認し、実WebViewで判定する。[S10]

### 特に先に直しておくとよい部品

- 戻るボタン：英語の「Back to search results」相当が入っても、題名や主操作を押し出さない。
- 削除確認：長い説明が入るときは縦方向へ伸ばし、操作を縦積みにできる。
- 保存エラー：読み終える前に消える短い通知だけへ押し込まない。
- 一覧カード：長い題名、日時、固定表示、抜粋が重ならない。
- ブランド文：日本語の改行数を英語にも強制せず、訳文ごとに行分けを設計する。
- 入力placeholder：装飾的に短くしすぎず、何を書ける場所か分かる。
- アプリ情報・ポリシー：文章量が増えても、最後のリンクまで到達できる。

翻訳後の長さは揃わないため、短い固定幅の容器とnowrapへの依存を減らす。文字数差をフォント縮小だけで吸収しない。[S11]

## 7. 翻訳の声：雰囲気と操作の意味を両立させる

### 用語の方針

名前はZanshinを共通のブランド表記候補にし、日本語では残心を使う。ストア名の空き状況や商標を調査した結論ではなく、表記設計の提案である。

記録の単位は英語ではnoteに統一する。trace、afterglow、spaceなどをあらゆる操作名へ使うと、保存・削除・復旧の対象が分かりにくくなる。詩的な言葉は、起動時、空の画面、短いブランド文に置く。

既存の英語「Place new words」「Untitled trace」等をそのまま正解として移植せず、前回採用した日本語仕様D16の意味から翻訳する。

### 日英の文案

以下は画面実装前の文案。意味、表示幅、読み上げ、母語話者の確認で確定する。

| 日本語の意味 | 英語案 |
|---|---|
| メモを書く | New note |
| タイトル（任意） | Title (optional) |
| 編集する | Edit |
| 一覧へ | Back to notes |
| 検索結果へ | Back to results |
| 読み返しへ | Back to reading |
| 先頭に留める | Pin to top |
| 先頭固定を解除 | Unpin |
| 保存中 | Saving… |
| 保存済み | Saved |
| 最新の変更を保存できませんでした | Your latest changes couldn’t be saved. |
| 通常の保存再試行 | Try saving again |
| このメモを削除しますか？ | Delete this note? |
| 削除する | Delete note |
| キャンセル | Cancel |
| 元に戻す | Undo |
| コピーする | Copy text |
| コピー成功 | Copied |
| この版を見る | View this version |
| 未保存の変更 | Unsaved changes |
| 検索結果がない | No notes match your search. |
| 言語 | Language |
| システム設定に従う | System default |
| 縦書き | Vertical |
| 横書き | Horizontal |

ブランド文の独立した候補：

- 「言葉を静かに置ける場所」：A quiet place for your words.
- 「思いつきも、一行も、書きかけも」：A thought, a line, or something unfinished.
- 入力の案内：Write what’s on your mind.

この3つをすべて同じ画面へ追加する必要はない。初回の空画面など、最も意味がある箇所に絞る。

### 異常時の意味を変えない

| 状態 | 翻訳で守ること |
|---|---|
| 本体の最新変更が未保存 | 「最新の変更が保存できなかった」と伝え、過去の成功表示と混ぜない |
| 本体は保存済み、端末内の復旧用コピーのみ更新失敗 | 本体成功を確認できたときだけ、その違いを説明する |
| 保存データの検査に失敗 | 「データが存在しない」「メモは0件」と訳さない |
| 復旧候補を閲覧 | 閲覧しただけで「復元済み」「保存済み」にしない |
| 0件の復旧候補 | 空の有効な保存版として扱い、「復旧できるものがない」と断定しない |
| 原文のコピー成功 | クリップボードへのコピーを示し、アプリ保存成功とは区別する |
| 削除・Undo | 対象と実際の確定状態を表す。言語切替でUndoの寿命を変えない |

端末内の復旧用コピーだけ失敗した場合の案：

“Your changes are saved. The on-device recovery copy couldn’t be updated.”

これは現在版の本体保存を確認できたときだけ使う。「バックアップ」という語から、クラウド同期や端末交換時の復元まで保証したと受け取られないようにする。

復旧画面のcountは、候補の版に入っているメモ数。例えば3なら「3つの復旧版」ではなく、“This version contains 3 notes.” の意味にする。引数名もnoteCountとversionCountを分ける。

### 翻訳者へ渡す情報

キー、原文、表示箇所、操作結果、差し込み値の意味、画面例をセットにする。保存・削除・復旧では「何が成功したか」「何が失われるか」を注記する。利用者が書いた実際のメモを翻訳資料に使う必要はなく、合成した例文で十分。

## 8. 実装の境界：小さく始めて増やせる形

日英の導入だけなら、大きな翻訳基盤は必須ではない。型付きの辞書、安定したReact Context、Intlのformatterで始める案が合っている。

| 責務 | 置き場所の例 |
|---|---|
| UiLocale / UiLanguagePreference / Messages | src/i18n/types.ts |
| 完成した日本語・英語辞書 | src/i18n/messages/ja.ts、en.ts |
| タグ照合とフォールバック | src/i18n/resolveLocale.ts |
| 実効言語の提供 | src/i18n/I18nProvider.tsx |
| 件数・日付 | src/i18n/formatters.ts |
| UI設定の読み書き | src/lib/uiPreferences.ts |
| nativeの現在アプリ言語取得 | 小さなCapacitor bridge |
| 例外時の最小辞書 | 通常Providerへ依存しない静的モジュール |

ファイル名は提案。実装中の構成に同じ責務があれば、二重に作らず合わせる。

### 辞書の型

現行のCopy = typeof copyは、as constにより日本語の文字列そのものを型として持つ。これをそのまま英語辞書の型へ流用しない。

型の概念例：

```ts
type UiLocale = "ja" | "en";
type UiLanguagePreference = "system" | UiLocale;

type Messages = {
  newNote: string;
  notesCount: (noteCount: number) => string;
  searchResultsCount: (noteCount: number) => string;
  recoveryVersionSummary: (noteCount: number) => string;
  saveFailedLatest: string;
  // 実装では保存・復旧・削除・aria等の必須キーも列挙する
};
```

辞書ごとの必須キー・引数を型で揃える。文言キーは画面上の意味を表し、訳文そのものをキーにしない。文字列の途中へ言語固有の語を継ぎ足さず、文全体を翻訳単位にする。

将来、言語数、翻訳者の作業、複数形・選択形が増えたら、i18next / react-i18next等を再評価する。複雑なメッセージ構文を独自実装しない。i18nextにも型付け・複数形・文脈単位の管理が用意されている。[S12]

### 保存の状態と翻訳を分ける

保存処理はreasonや対象版を保持し、表示側で現在の辞書へ変換する。getSaveFailureMessageKeyのような意味の変換を挟めば、言語切替後も同じ失敗を新しい言語で表示できる。

訳済み文字列を状態の識別子や保存結果として使わない。翻訳関数が変わったことを理由に、保存・復旧probe・候補比較を再実行しない。

### 起動とオフライン

日英辞書はアプリへ同梱する。言語を切り替えるための通信、ログイン、利用者の本文送信は不要。本文編集の途中で翻訳ファイルの取得待ちに入らない。

設定読込みに時間がかかる場合は、初期表示言語の確定手順を用意する。誤った言語でフォームを一度作ってから別のフォームへ入れ替える構造にせず、入力開始前のbootstrapと安定したUIツリーを使う。設定障害で起動自体が止まらない短いフォールバックも必要。

### AppErrorBoundaryの独立性

通常の翻訳Providerが壊れたときも、例外画面は表示できるようにする。解決済み言語と最小辞書を安全な位置から利用し、言語設定が読めないだけで最新原文のコピー・取り出しを止めない。これは前回W1の原文救済を多言語へ広げる部分である。

## 9. 言語切替で文章を失わない

アプリ内で言語を切り替えるときは、同じコンポーネントとDOMを保って表示文言を更新する。Reactはkeyやツリーの位置によりstateの寿命を決めるため、localeをAppや入力欄のkeyに使うと状態が作り直される。[S13]

実装上、次を避ける。

- AppやNoteEditorへlocale依存のkeyを付ける。
- 言語切替のためにwindow.location.reloadを呼ぶ。
- 既存メモを再読み込みして、編集中の状態を差し替える。
- 復旧候補・競合待ち・保護中の状態を初期化する。
- 設定の保存成功を、本文の保存成功として扱う。

維持するのは、題名・本文・選択範囲・対象メモ、検索語・結果位置・戻り先、保存対象版・失敗理由、screen/local/nativeの候補、確認ダイアログの対象、Undoの残り時間。

日本語や韓国語の変換中に外部の言語変更イベントが来た場合、入力欄を差し替えない。必要なら変換確定までUI言語の反映を待つ。具体的なIMEイベント順序は実iPhoneで確認する。

OS設定でアプリ言語を変える経路は別に確認する。アプリから設定へ案内する前に、現在版の保存成功を確認する。保存失敗・競合待ちなら、その状態を伝え、原文の確認・コピー等と、設定へ移らず戻る導線を用意する。コピー成功はアプリへの保存成功と表示しない。

既存W1の描画境界外での下書き保持は、プロセス再起動を越えた未保存版の永続化を保証するものではない。本体保存に失敗した版がnativeへ代替保存されるとも仮定しない。OSから直接言語を変更した場合まで、RAMにしかない文章を再起動後に戻せるとは説明しない。未保存版の自動復帰まで求める場合は、独立した永続下書きの設計と障害時検証を追加する。再起動後は、確定済みの版と実装した保全範囲を確認する。

## 10. 検索・件数・日付・文字の区切り

### 検索の最小方針

比較用の文字列だけNFC正規化し、UI言語に依存しない小文字化を使う。原文はそのまま保存する。

| 保存本文と検索語 | 日英版で推奨する意味 |
|---|---|
| café / cafe＋結合アクセント | 同じ正準表現として一致 |
| が / か＋結合濁点 | 一致 |
| café / cafe（アクセントなし） | 初期方針では別。勝手にアクセントを落とさない |
| ＡＢＣ / abc | 初期のNFCだけでは一致しない。全角半角の同一視は別判断 |
| I / i、I / ı | 固定方針で判定し、UI変更で結果を変えない |
| ß / ss | 単純な小文字化では同一視されない。高度な言語別検索は別段階 |

NFCは正準等価な表現を揃え、NFKCはさらに互換文字の区別を折り畳む。検索の都合で原文へNFKCを適用しない。濁点やアクセント等の結合記号を一律除去する設計にも注意が必要。[S14]

ハイライト・抜粋では、正規化後の位置をそのまま元本文の位置として使わない。最小構成では、一致した行を探してその行の原文を出す方法もある。あとから精密なハイライトを付けるなら、原文への位置対応を管理する。

### 件数と複数形

件数の文を丸ごと辞書へ入れる。数値はIntl.NumberFormat、複数形はIntl.PluralRules等を使い、UI側で英語のsを付け足さない。

- 一覧：1 note / 2 notes
- 検索：1 note found / 2 notes found
- 復旧：This version contains 1 note. / This version contains 2 notes.
- 0件：一覧、検索、復旧で意味を分ける

現在の「数＋つの＋余韻」のような構成を見直し、日本語側の数え方も整える。数値の書式と文法上のカテゴリは、国際化APIの別の役割として扱う。[S15]

### 日付と時間帯

日付印のYYYY.MM.DDを、残心の共通の視覚表現として保つ案は成立する。その場合でも、読み上げには「作成日」と曖昧でない日付を付け、詳細説明の日時はlocaleに応じて表示する。

朝・昼・夕・夜は、内部でmorning/afternoon/evening/nightという意味を返し、表示側で訳す。英語の自然さは“Morning”などの簡潔な案から確認する。「余白」をすべてspaceと直訳しない。

既存の時間区分は5〜10時、11〜15時、16〜18時、19〜4時。言語を変えるだけで区分や時刻を変えない。境界を変更する場合は独立した仕様変更として扱う。

UI言語のenを、米国の地域設定や米国のタイムゾーンと同一視しない。必要な地域タグはformatterへ別に渡せるようにし、保存済みのISO日時は書き換えない。Intl.DateTimeFormatでも言語・書式・timeZoneは異なる指定である。[S15]

前回R37の作成時タイムゾーン保存・移行は保留を維持する。過去のメモについて、作成時の国やタイムゾーンを推測して追加しない。

### 絵文字と「一文字」

抜粋や題名候補の切り詰めは、見た目の一文字のまとまりを壊さない。家族絵文字、肌色、国旗、アクセント、結合濁点を例にする。JavaScriptのlengthやsliceだけでは、このまとまりを表せない。Unicodeではこの区切りをgrapheme clusterとして扱う。[S16]

Intl.Segmenterを使う場合は利用可能性を確認する。WebKitでの導入はSafari 14.1 / iOS 14.5世代であり、リポジトリのiOS 14.0設定と差がある。[S17]

対応案は、機能検出と必要なフォールバックを設ける、または最小OSを別途判断すること。APIを使うためだけに無断で対応OSを引き上げない。Array.fromはサロゲートペアには対応できても、すべての結合絵文字の代替にはならない。必要なら信頼できる分割実装を選ぶか、原文のJS切断を避ける表示方法にする。

## 11. 読み上げと左右方向

### UIと本文のlangを分ける

htmlのlangは実効UI言語へ合わせる。ボタン、検索結果件数、保存通知、復旧候補の説明、読み上げ専用ラベルも翻訳する。

利用者の本文は日本語・英語・混在文のどれか分からない。旧Note.localeやUI言語から本文の言語を断定しない。HTMLではlang=""が言語不明を表すため、UIのlangを本文へそのまま継承させない候補になる。ただし、これだけでVoiceOverが全言語を正しく読むとは保証できない。実際の読み上げ確認を受入に含める。[S18]

本文言語の明示指定が将来必要になった場合も、メモ作成時の必須入力にはしない。必要な人が任意に指定できる別の表示情報として検討する。

### 題名と操作ラベル

現在の「題名＋日本語の読点＋操作名」のaria-label組立てを見直す。本文由来の題名と言語が分かるUIラベルを分けて構造化し、未知の本文全体へ英語の発音を強制しない。

保存状態の読み上げは意味のある変化に絞る。言語切替時に全カードを大量に読み上げ直さない。フォーカスは変更した設定項目に残り、戻るときは元の場所へ戻す。

### RTLの基礎は日英版にも必要

日英UIの利用者でもアラビア語のメモを書く可能性がある。利用者が入力した題名・短い断片はbdi等で周囲から分離し、本文や入力欄にはdir="auto"などを適切に使う。URL、数字、括弧、引用符が混じった例を確認する。dir="auto"は強い文字の並びを手掛かりにするため、文書全体の言語理解を代替するものではない。[S02]

余白や配置のstart/endを使える箇所は論理方向のCSSへ寄せる。ただし、縦書きの「次の列が物理的に左にある」といった意味まで機械的に置換しない。

アラビア語UIの正式対応は、メニュー・ナビゲーション・アイコン・フォーカス・ジェスチャーのRTL確認を伴う別段階。本文が表示できることだけで、UIも完全対応と宣言しない。

## 12. iOS・ストア・情報ページを揃える

### native側

日英を完成させたリリースでは、次を同じ言語集合に揃える案とする。

| 項目 | 提案 |
|---|---|
| Web側の完成辞書 | ja / en |
| CFBundleLocalizations | ja / en |
| CFBundleDevelopmentRegion | en |
| Xcode knownRegions | en / ja / Base |
| 未対応言語でのWeb fallback | en |
| 現在のアプリ言語取得 | Bundle.main.preferredLocalizationsを小さなbridgeで渡す |

CFBundleLocalizationsは、アプリが手動で扱うローカライズの宣言にも使われる。developmentRegionはフォールバックに関わるため、Archive内の値とWeb側の既定を照合する。[S19][S20]

現在のプロジェクトはdevelopmentRegionがenでも、Webは日本語固定。値がすでにenであることを、英語版完成の証拠にはしない。

Capacitorのローカルnative pluginで必要な情報を渡す構成は公式に案内されている。端末識別子や位置情報を言語選択に追加する必要はない。OS設定を書き換える私的な方法を使わず、公開された情報から実効言語を決める。[S21]

### アプリ名

日本語では「残心」、英語で「Zanshin」と表示する案はある。ただしアプリ内のブランド、ホーム画面表示名、ストア掲載名は別々に管理する。実際に採用する名称と短縮表示は実機とApp Store Connectで確認する。

### ストア掲載

App Store Connectの説明文を翻訳しても、バイナリ内の対応言語が自動的に増えるわけではない。逆に、辞書を追加しただけでストア説明・画像が翻訳されるわけでもない。Appleも両者を分けて説明している。[S22]

英語公開時に揃えるもの：

- アプリ名・サブタイトル・説明文・更新説明など、採用した掲載項目。
- 実際の英語UIを使ったスクリーンショット。
- 英語で開けるサポートとプライバシーの案内。
- 審査担当が言語変更と復旧経路を確認できる説明。
- 提出するArchive、画面画像、対応言語の宣言の一致。

新しいストア言語を作ると、主言語の画像が引き継がれることがある。英語欄ができたことだけで英語のスクリーンショットまで用意できたと判断しない。[S22]

ストアの主言語は日本語のままでもよい。アプリ内の未対応言語fallbackをenにする判断と、ストア主言語は別。

### サポート・プライバシー

英語で書き始めた人が困ったときに、日本語の説明しか読めない状態を避ける。アプリ内の説明とpublicのページを同じ内容へ揃え、両言語への戻り道を設ける。

英語案内には、端末内保存、復旧用コピーの範囲、削除・アンインストール等に関する実装に即した説明、実際に管理している問い合わせ先を載せる。機能・保全範囲を広く見せる表現は加えない。

これは本提案の品質条件であり、「Appleがすべての言語への全文翻訳を一律義務付けている」という主張ではない。ページの公開やストア提出は、実装と内容が確定した段階で行う。

## 13. 進行中のW0〜W5との接続

既存の[ストア品質改善設計](https://github.com/sunpotflower4460-cpu/AAA-opus4.7/blob/6b40f44fe630b094aa0aad4fb1e79f5def3bc5b9/docs/store-release-polish/README.md)と競合しないよう、まず保存の契約と画面の骨格を安定させる。

### 今、実装担当へ共有するとよい制約

1. UI文言を意味のまとまりで集め、保存状態はコードで扱う。
2. 操作UIの書体・方向と、利用者の本文の書体・方向を分ける。
3. 横書きの読み返しを英語対応の必須条件として見込む。
4. 長い訳文と200%文字拡大を受け止める幅・高さにする。
5. 言語・読書方向の設定をNoteへ保存しない。
6. 原文救済・復旧候補・Undoを、言語変更で初期化しない。

これらは今のレイアウト・保存表示の実装に織り込める。一方、App.tsxやReadMode.tsxの広範な辞書置換は、同じ箇所のW1〜W3作業と担当範囲を調整してから行う。

### 多言語化の作業単位案

| 段階 | 実装・確認 | 完了の判断 |
|---|---|---|
| I0 最新実装との照合 | W0〜W5の変更を読み、既存の辞書化・横書き・設定を確認 | 重複実装と旧仕様への巻戻しがない |
| I1 日英の表示基盤 | Messages、辞書、言語解決、設定、安定したProvider | 全必須キーと引数が揃い、未保存状態を保って切替できる |
| I2 読み方と文字組み | 横書き、縦書き、表示設定、長い訳文、文字拡大 | 日英の長文・短文・混在文を末尾まで読める |
| I3 操作全体の完成 | 保存・復旧・削除・検索・件数・日時・読み上げ | 正常時と異常時を日英で完了できる |
| I4 nativeと掲載準備 | bridge、bundle設定、情報ページ、英語画像・説明 | アプリ・Archive・掲載情報の言語が一致する |
| I5 同じ版での統合確認 | 最低対応OSと現行OS、実機、校閲、TestFlight | 実装済みと実機確認済みを区別した証拠が揃う |

必要な設計検討は今進め、広い実装変更はW1の保存契約・W2/W3の読み方と入力の境界が定まってから重ねる。

### 採用時に既存文書へ反映する箇所

| 文書 | 変更する意味 |
|---|---|
| README | 「日本語UI完成」の初版範囲を、日英リリースの範囲と時期に合わせて更新 |
| DESIGN D04 | 横書きを英語対応の完成条件へ引き上げる |
| DESIGNの文字・情報・支援技術・保存・復旧・文言の章 | 本文とUIの分離、lang/dir、辞書、訳文、nativeの言語方針を追記 |

## 14. 多言語版の受入条件案

以下は追加仕様の提案。実装後の確認記録では、対象コミット、OS、端末・画面サイズ、操作、結果を残す。未実施を合格扱いにしない。

| ID | 条件 | 合格の基準 |
|---|---|---|
| ML01 | 辞書の整合 | 日英で必須キー・引数が揃い、公開UI・aria・保存失敗・復旧・削除・例外画面に欠落がない |
| ML02 | 言語解決 | ja-JP、en-GB、未対応先頭＋後続ja、不正タグ、空候補で期待した言語になる |
| ML03 | 設定の競合・失敗 | 遅い読込み、en→jaの連続選択、設定保存失敗でも最後の選択と本文状態を保つ |
| ML04 | メモの不変 | 言語だけの変更で本文・題名・時刻・印・復旧rawが変わらない |
| ML05 | 通常編集中 | 保存待ち、途中挿入、選択、スクロール中に言語変更しても欠落・重複・再マウントがない |
| ML06 | IME中 | 日本語かな変換と韓国語入力で、確定文字・選択範囲・保存対象版が保たれる |
| ML07 | 保存失敗中 | 容量不足・利用不可・検査失敗・競合の意味と再試行操作が新しい言語で残る |
| ML08 | 復旧比較中 | screen/local/nativeの候補と選択中の版が残る。0件の候補を有効に扱う |
| ML09 | 削除とUndo | 確認対象、結果、残り時間を言語変更で初期化・延長しない |
| ML10 | 読み方の保持 | UI変更で縦横は変わらない。明示的な縦横切替では同じ文章付近へ戻れる |
| ML11 | 新旧導入 | 既存選択を継承し、旧版は従来表示、新規は一度だけ初期値を決める。0件を新規判定にしない |
| ML12 | 長文と混在 | 日本語2000字、英語2000語、200字のURL、空行のある詩で全文・改行・コピーを保つ |
| ML13 | 件数 | 0/1/2/11/1000で一覧・検索・復旧それぞれの意味と文法が正しい |
| ML14 | 検索 | caféの結合表現、がの結合表現で一致。UI切替で結果が変わらず、原文は不変 |
| ML15 | 文字分割 | 絵文字ZWJ・肌色・旗・結合アクセントを途中で切らない。Segmenter不在でも起動・表示が保たれる |
| ML16 | 日付 | 日付境界・時間帯境界で意味が合い、UI変更だけでは保存日時やタイムゾーンを変えない |
| ML17 | 文字量 | 375×667、390×844、430px幅の比較と200%文字拡大で主要操作・説明が欠けない |
| ML18 | 読み上げ | 日英UI、英語UI＋日本語本文、例外画面、復旧候補で、読み順と操作名を確認する |
| ML19 | 左右混在 | アラビア語の合成メモ＋英語URL＋数字＋括弧を、日英UIで編集・読書・コピーできる |
| ML20 | オフラインと障害 | 通信なしで辞書切替と原文救済が動く。言語設定異常だけで起動不能にならない |
| ML21 | iOSのアプリ言語 | 端末ja＋アプリen、端末en＋アプリjaを確認。独自overrideとnativeメニューの組合せも確認する |
| ML22 | OS設定経由の変更 | 案内前に現在版の保存を確認。失敗・競合時は原文取り出しと移動中止を提示。再起動後の確定済み版を保つ。未保存版の永続化は別要件として記録する |
| ML23 | 疑似翻訳 | JavaScript辞書を倍程度に伸ばし、アクセント付き・境界付きの表示で欠けや未抽出文言を発見できる |
| ML24 | 提出する版 | 最低対応OSと現行OSで確認し、Archiveの言語宣言、実UI、説明、画像、サポートが同じ対応範囲になる |

疑似翻訳は開発用に限定し、製品の言語選択肢には出さない。Xcodeにも文字量や方向を変える疑似言語が用意されるが、このアプリのJavaScript内の独自辞書まで自動変換されると想定しない。Web辞書側にも検査用データを用意する。[S23]

自動化する価値が高いのは、言語解決、辞書の引数・必須キー、言語変更時の保存状態、Unicode検索、設定読込みの競合。文字組み・IME・VoiceOver・native設定の確認は実機を含める。

単に各辞書の文字列を一つずつ写して比較する大量のテストより、「誤ると本文や操作の意味が変わる境界」を優先する。

## 16. 採用する判断の要約

| 判断 | 推奨 |
|---|---|
| 最初の言語 | 日本語・英語 |
| 世界観 | 紙・墨・月・余白を共通にし、文字組みと操作の説明を各言語へ合わせる |
| 英語の読み返し | 横書きを完成条件にする |
| UI言語と本文 | 別に扱い、保存原文は変えない |
| 切替 | system / 日本語 / English。アプリ内変更とOS変更を別に検証 |
| 保存設定 | Note・journalから独立し、本文保存の成功表示と混同しない |
| 実装 | 型付きの同梱辞書＋安定したProvider＋Intlから始める |
| 検索 | 比較用NFCと固定の大小文字方針。原文は不変 |
| 異常時 | 保存・復旧・削除・例外画面まで日英で揃える |
| ストア | バイナリの対応言語、掲載文、実UI画像、支援ページを同じ版で確認 |
| 追加言語 | 日英の完成後、要望と校閲体制に応じて1言語ずつ |
| 進行中の実装 | W1〜W3の契約・骨格と調整し、確認済みの修正を巻き戻さない |

多言語化によって、英語を書く人にも、日本語で詩を書く人にも、同じ落ち着いた場所を渡せる。言葉の見え方はそれぞれに合わせながら、書いた内容と安心して戻れる体験を共通の中心に置く。
