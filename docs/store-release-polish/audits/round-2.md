## 3. R31 — 縦書きは「スクロールを許す」だけでは整わない

### 現在の構造

読み返しの紙面には、次の組合せがあります。

~~~css
.read-mode-paper {
  display: flex;
  writing-mode: vertical-rl;
}
~~~

この要素のflex-directionは指定されていないため、既定のrowです。rowは物理的な横方向を意味するのではなく、その要素のinline軸に沿います。vertical-rl・通常のltrではinline軸が上から下なので、子要素の日付、タイトル、区切り、本文は、その方向へ並ぶflexアイテムになります。[実装][src-read-css] [W3C Flexbox][w3c-flex] [W3C Writing Modes][w3c-writing]

つまり、本のようにタイトルと本文を右から左へ順に読ませる設計に対し、親のレイアウト方式が一致していません。前回指摘したoverflowの上書きを解消した後にも、この構造は残ります。

### 区切り線が要求する高さ

区切り線にはmin-height:34px、margin-inline:21pxがあります。この要素も縦書きを継承しているため、margin-inlineは上下の余白です。指定値上、区切りだけで最低34＋21＋21＝76pxの縦方向の寸法を要求します。[区切りの指定][src-read-css]

最終的な文字の見え方はflexの縮小計算、内容、フォント、描画エンジンによって変わります。76pxを根拠に「本文が必ずその分だけ押し出される」「何文字欠ける」とは断定しません。ただし、区切り線が本文の縦方向の場所を使う構造であることは明確です。

### スクロールの軸も統一する

後段CSSにはoverscroll-behavior-inline:containとscroll-snap-type:x proximityが併記されています。縦書きのinlineは物理的な縦方向、xは横方向です。横へ読む面のスクロール連鎖を抑制したいなら、物理方向のx、または縦書きのblock方向へ揃える必要があります。[後段CSS][src-phase29] [W3C Overscroll Behavior][w3c-overscroll]

### 推奨する構造

1. 戻る・編集の操作は、横書きの操作バーに置く。
2. 日付は小さな横書き情報として独立させる。
3. タイトルと本文を、一つの縦書き文書として右から左へ流す。
4. 文書の横スクロールを受け持つ領域を一つにする。
5. 初版は連続スクロールを基本にし、途中で指を離した位置を保つ。
6. 実際に続きを隠している時だけ、続きがあることを示す。

タイトルと本文の2要素にsnapを付けても、文章全体がページ分割されるわけではありません。ページ送りの体験を作るなら別の設計が必要なので、まず連続して読める状態を安定させる方が変更範囲を絞れます。

**受入条件：** 1行、長いタイトル、空行の多い文章、2,000字の本文を使い、右端の冒頭から左端の末尾まで読める。タイトルの長さによって本文の行長が短く押し縮められない。編集から戻っても、読んでいた内容を見失わない。

## 4. R32 — キーボードが出た時の「書く場所」を優先する

### 本文より前に積まれる高さ

375×667のCSS viewport、標準文字サイズ、上下のsafe-areaが21px以下と仮定すると、現在の指定値から本文開始までの自然寸法は次のようになります。これは自動スクロール前の概算で、実機測定ではありません。前回の透明な55px要素は計算から除外しています。

| 要素 | 概算 |
|---|---:|
| 上側safe-area用余白 | 21px |
| 編集画面の上余白 | 13px |
| 操作バー | 52px |
| 操作バーと紙面の間 | 21px |
| 紙の上余白 | 34px |
| 日付2行 | 約34px |
| 日付の後 | 34px |
| タイトル1行 | 約39px |
| 区切り線とその前余白 | 22px |
| 本文前の余白 | 34px |
| **本文開始まで** | **約304px** |

根拠：[編集画面][src-editor]、[画面外枠][src-shell]、[基礎CSS][src-index]、[最終段階の寸法指定][src-phase29]。

本文の最小高さ42dvh、紙の下余白、保存表示、下側余白を加えた自然寸法は、この仮定で約702pxです。仮にキーボードが291pxを占めて可視領域が376pxになり、本文開始位置が変わらなければ、本文に残るのは約72pxです。

これは「実機で2行しか見えない」と確認した結果ではありません。OSが入力欄を見せようと画面を移動した時に、操作バーやタイトルとの関係がどうなるかを重点的に確認すべき根拠です。

### dvhへの置き換えだけでは完了しない

W3Cのviewport単位の説明には、画面を覆うUIがviewport単位を変化させない場合があり、ソフトウェアキーボードがその例として示されています。Capacitor 7のKeyboard公式資料でも、Native、Body、Noneでリサイズ対象が異なります。[W3C viewport単位][w3c-viewport] [Capacitor 7 Keyboard][cap-keyboard]

現リポジトリにはKeyboardプラグインや独自のvisualViewport処理がなく、キーボード表示時の寸法をアプリ側で明示的に制御していません。プラグインが無いこと自体を不具合とは数えません。まず実WebViewの挙動を確かめ、その結果に合う方式を選ぶ必要があります。[依存関係][src-package] [Capacitor設定][src-capconfig]

### 推奨する二つの状態

| 項目 | キーボードを閉じている時 | 入力している時 |
|---|---|---|
| 日付 | 小さな日付印として見せる | 1行へまとめるか、本文を妨げない位置へ |
| タイトル | 任意の題名として見える | 大きな空欄を維持し続けない |
| 紙の内側の余白 | 読み返しに合う余裕を持たせる | 本文周辺を広く使えるよう調整 |
| 保存表示 | 安定した位置に短く出す | 操作バー付近など、キーボードに隠れにくい位置 |
| スクロール | 文書を自然に見られる | カーソル周辺を保ち、主体を一つにする |
| 入力欄 | 同じ要素を維持 | 変換中にDOMを差し替えない |

通常文字サイズでは、キーボード表示中も本文4〜6行程度を見通せることを目標にできます。文字拡大時まで同じ行数を保証するために文字を縮める設計にはしません。

スクロール方式は、操作バーを独立させ、その下の編集領域全体をスクロールする案が有力です。その場合はtextareaを内容に合わせて伸ばし、ページとtextareaの両方を同時に動かす状態を常態化させないようにします。長文性能と選択操作は、この方式へ変えた後に実機で確認します。

**受入条件：** 375×667と390×844相当の画面で、かな・英語・絵文字のキーボードを使う。末尾への入力、途中挿入、複数行選択、変換候補選択、キーボード開閉を行い、カーソルと戻る操作に到達できる。

## 5. R33 — 描画エラー後にも、最後に書いた文章へ届くようにする

**条件を作って再現済み。アプリが自然にクラッシュする原因を発見したという指摘ではありません。**

保存済みメモを編集し、入力が画面へ反映された100ms後、通常の500ms保存を待たずに子コンポーネントへ描画例外を注入しました。

AppErrorBoundaryはエラー画面へ切り替わり、その内側のAppを破棄します。Appが持つ保存タイマーとlifecycle購読も解除されます。その後5秒待ち、pagehideを送っても、新しい本文はprimary、backup、pending journalのどこにもありませんでした。エラー画面の操作は再読み込みだけです。[起動構造][src-main] [ErrorBoundary][src-boundary] [保存タイマーと解除][src-app-autosave]

この時点では、最新の文章を持つtextareaもなくなっているため、利用者が手動でコピーすることもできません。正常保存が続いている時は直近の保存待ち時間が中心ですが、保存失敗中に同じことが起これば、未保存の範囲は長くなり得ます。

### 改善方針

表示部分が壊れても、最後に受け取った編集内容をエラー画面から参照できる構造にします。例えば、最後の下書きの保持や保存制御を、表示エラーで破棄される範囲の外へ置きます。

最低限の完成条件は、エラー画面から未保存本文を読み取り専用で表示・コピーできることです。既存の保存データと競合している場合は、その判定を維持して保存を止めます。再読み込みを提案する場合も、現在の未保存変更の扱いが分かる必要があります。

一律のunmount時強制保存は勧めません。復元中・競合中まで無条件で上書きしてしまう変更では、既存の保護を損ないます。

**受入条件：** 通常の保存待ち、容量不足で保存失敗中、競合解決待ちの3状態で描画例外を注入し、未保存本文を取り出せる。復旧操作が既存データを無断で上書きしない。

## 6. R34 — 保護のために保存を止めた後、解決まで進めるようにする

**復元用の2つの退避枠が別世代で埋まっている条件で再現済み。**

primaryが無く、正常なbackupと、異なる2つの保護候補がある状態を作りました。backupから表示された復元候補を少し編集し、「この画面の内容で保存し直す」を2回押しました。

結果として既存の3候補は守られましたが、primaryは作られず、現在の編集は画面内だけに残りました。画面には同じ復元案内と同じ保存ボタンが出続けます。

保存層は未確認の候補を失わないよう停止しています。しかし、戻り値が通常の競合と同じconflictであるため、UIに「退避枠が満杯」という理由が伝わりません。過去候補を確認・持ち出し・整理する画面もありません。[保存層の満杯判定][src-storage-archive] [復元操作][src-app-recovery] [既存のPhase 39報告][src-phase39]

### 改善方針

保存結果に「保護候補がいっぱい」という区別を設け、通常の版の競合と分けて案内します。その上で、現在の本文を保ったまま、候補の確認、必要な内容の持ち出し、利用者が確認した候補だけの整理、現在版の保存まで進められるようにします。

「再試行してください」とだけ伝えても、条件が変わらなければ保存できません。候補を自動で削って空きを作る方法も、現行の保護方針と合いません。

小さく直す一案は、復元候補をまず正本として確定してから編集する流れです。ただし、異なるnative候補を選ぶ場合などは残るため、それだけで満杯条件を解決したとは扱えません。

**受入条件：** 2枠満杯の状態から、現在の編集と過去の候補を失わず、利用者が画面上の操作で保存完了まで進める。

## 7. R35 — 保存表示は「いま見ている文章」に対して一つにする

**古いnative予備保存失敗と、新しい本体保存失敗を重ねて再現済み。**

次の順に状態を変えました。

1. 以前のメモ本体は保存されている。
2. native側の予備保存を失敗させる。
3. 本文を新しく編集する。
4. 今度は本体のlocalStorage保存も容量不足で失敗させる。

この時、同じ画面に次の2つが表示されました。

> メモ本体は保存されていますが、端末内の予備保存を更新できませんでした。

> 保存領域の上限に達したため、保存できませんでした。

画面には新しい本文があり、保存先には以前の本文が残る状態です。以前の保存分が存在するという意味では前者も成立しますが、利用者が知りたいのは、現在見ている文章が保存されたかどうかです。[native結果の保持][src-app-native] [案内の表示条件][src-app-banner] [文言][src-copy]

### 改善方針

保存表示は「表示中の編集版」「本体へ保存できた版」「予備保存できた版」の関係から決めます。全ての内部情報を利用者に見せる必要はありませんが、表示の判断にはどの版への結果かが必要です。

| 実際の状態 | 主に伝えること | 次の操作 |
|---|---|---|
| 最新版を保存中 | 保存中 | 通常操作を続けられる |
| 最新版を本体へ保存できなかった | 最新の変更を保存できませんでした | 再試行。解決しない時は本文を取り出せる |
| 最新版は本体へ保存済み、予備保存のみ未更新 | 最新の変更は保存済み。予備保存を更新できませんでした | 予備保存の再試行 |
| 別の候補と競合して停止 | 内容を確認するため、保存を止めています | 候補を見比べる |
| 最新版も予備保存も完了 | 保存済み | 短く表示して静かに戻す |

本体に未保存変更がある間は、以前の予備保存警告を補助情報に下げます。本体保存が成功した後で、予備保存だけ未更新なら、その状態を改めて出します。

**受入条件：** nativeだけ失敗→入力→localも失敗→local成功→native成功と遷移させ、どの段階でも現在の文章に対する誤った保存済み表示を出さない。編集・読み返し・一覧の移動でも、その事実を引き継ぐ。

## 8. R36 — 保存の途中に必要な余裕と、容量不足からの出口

### 実関数で測定したこと

現在の通常保存は、全メモのJSONを本体と復旧コピーに残しながら、旧版と新版を含むjournalを書きます。journal→復旧コピー→本体の順で確定し、その後journalを消します。[通常保存処理][src-storage-save]

本文2,000文字の合成メモを作り、そのうち1件の本文へ1文字追加して、実際のsaveNotes関数を呼びました。

測定対象はlocalStorageの値文字列長の合計です。単位はUTF-16コード単位で、キー名・他データ・実装内部の管理領域を含みません。ディスク使用バイト数や実端末の容量上限を測定した表ではありません。

| 合成メモ数 | メモ全体のJSON長 S | 保存前の定常量 | 保存中のピーク | ピーク / S |
|---|---:|---:|---:|---:|
| 30件 | 64,912 | 129,824 | 261,276 | 約4.03倍 |
| 300件 | 649,393 | 1,298,786 | 2,613,240 | 約4.02倍 |
| 1,000件 | 2,164,894 | 4,329,788 | 8,711,644 | 約4.02倍 |

定常状態は本体と復旧コピーで約2倍です。保存中は、それに旧版・新版を含むjournalが加わるため、今回のデータでは約4.02倍まで増えました。改行・引用符などのエスケープで割合は変わり、4.02倍が全データ共通の定数ではありません。競合archiveが残っていれば、その分はさらに加わります。

### 「不要メモを消せば直る」とは限らない

300件の合成データに、Sの2.5倍というモデル上限を設定しました。現在の定常量も、1件削除した後の定常量も、その上限内です。しかし、削除を記録するjournalの書込みで容量不足となり、本体を更新する前に停止しました。

| 指標 | UTF-16コード単位 |
|---|---:|
| 現在の定常量 | 1,298,786 |
| モデル上限 | 1,623,483 |
| 1件削除後に必要な定常量 | 1,294,460 |
| 削除journal追加時に必要な量 | 2,611,048 |

容量条件を変えず再試行すると、同じ箇所で失敗します。今回の条件では、Undoで元の保存済み内容へ戻す操作は、追加書込み不要のno-op経路で成功しました。

この検証は「300件でiPhoneがいっぱいになる」という意味ではありません。**最終的にはデータを減らす操作でも、途中に必要な余裕がないと確定できない**という現行方式の性質を示しています。

本体保存に失敗した今回の編集版は、native予備保存へ引き継がれません。以前から投入済みのnative処理が動く可能性はありますが、別の予備保存層があることで、この容量不足が自動的に解決する設計ではありません。[保存成功後のnative連携][src-app-save-result]

### 改善方針

公開前には、想定する文章量で実機の上限・保存時間・失敗時の動作を確認します。容量不足の案内は、不要メモの削除だけを解決策にしないことが必要です。

直近の仕上げでは、未保存の文章をコピーまたは安全に書き出せる経路と、以前保存した版との区別を整える価値が高いです。長期的には、1メモ単位の更新やトランザクションを持つ保存方式も検討できますが、公開直前に保存方式を大きく変更するかは、測定と移行検証の結果で判断します。バックアップや競合保護だけを取り外す修正は勧めません。

**受入条件：** 十分な余裕、journal書込み失敗、復旧コピー書込み失敗、本体書込み失敗を分け、現在の文章と以前保存した文章のどちらにも必要な時に到達できる。削除で空きを作れない条件も含める。

## 9. R37 — 日付印は「書いた時のしるし」かを決める

日付印はcreatedAtを、閲覧時の環境のgetFullYear、getMonth、getDate、getHoursで表示しています。保存モデルには作成時のタイムゾーンがありません。[日付印関数][src-date] [メモ型][src-note-type]

同じcreatedAt、2026-11-25T15:30:00.000Zを実関数へ渡した結果です。

| 表示環境のタイムゾーン | 日付印 | 時間帯 |
|---|---|---|
| Asia/Tokyo | 2026.11.26 | 夜の余白 |
| Pacific/Honolulu | 2026.11.25 | 朝の余白 |
| Europe/London | 2026.11.25 | 昼の余白 |

時刻としては同じ瞬間なので、現在地に換算する方針なら自然な結果です。一方、「その時に紙へ残した日付印」を表したいなら、旅行先などで過去の夜が朝に変わることになります。

ここは公開前の重大不具合というより、製品の意味を決める箇所です。作成地の日付印を保つなら、新規メモから作成時のタイムゾーンまたは日付印情報を記録します。既存メモの作成地は復元できないため、現在地を過去の作成地として断定する移行はしません。

## 10. 画面を横断して揃える、4つの約束

ここからは改善仕様の提案です。利用者調査で効果を測定済みの内容ではありません。

1. **ひとことから書ける。** 題名や完成した文章を要求しない。
2. **書いた内容が、そのまま残る。** 表示や検索の都合で原文を改変しない。
3. **自分の言葉を落ち着いて読める。** 本文を中心に、必要な操作を見つけられる。
4. **途中で離れて、続きを始められる。** 読み返しや保存演出を、終了の条件にしない。

この基準で、前回の見た目に関する指摘も一貫して修正できます。

### 10.1 ホームの3状態

| 状態 | 情報の順序 | 役割 |
|---|---|---|
| 空 | 小さなアプリ名・短いコピー→作成操作→端末保存の補助説明 | 書いてみるまでの迷いを減らす |
| 通常 | コンパクトなアプリ名→検索→自分のメモ | 毎回、自分の言葉に早く届く |
| 検索 | 検索語→件数→一致部分を含むメモ | なぜこのメモが見つかったか分かる |

現状は通常状態でもブランド導入を繰り返し、空状態には異なる名称の作成操作が併存しています。[一覧][src-list] [空状態][src-empty]

空状態には、例えば次の文章で十分です。

> ひとことでも、途中のままでも。  
> 入力した内容は、この端末に自動保存されます。

アプリ側のコピーを減らした分、自分のメモを最初に見られるようにします。全件削除後にも同じ空状態を使える表現なら、初回フラグを増やす必要もありません。

メモ数が増えるたびに操作位置を変える設計にはせず、空・通常・検索の基本構造を固定します。

### 10.2 タイトル任意を、一覧から読み返しまで通す

現在の新規メモは本文へフォーカスする一方、題名入力は「この余白に名をつける」、無題は「名のない余韻」と表示されます。[編集画面][src-editor] [カード][src-card] [読み返し][src-read]

次の表示契約にすると、一文でも自然に成立します。

| 内容 | 一覧での識別 | 読み返し | 保存データ |
|---|---|---|---|
| 題名あり | 本人の題名 | 本人の題名＋本文 | 原文のまま |
| 題名なし・本文あり | 最初の非空行を識別用見出しに使う | 架空の大きな題名を加えず本文から読む | タイトルは空のまま |
| 題名のみ | 題名 | 題名だけで成立させる | 本文が空でも保存可能 |
| 新規で一切未操作 | 一覧へ確定しない | 読み返しへ進める必要はない | 未操作下書きとして処理 |
| 既存メモを本人が空にした | 既存のメモとして扱う | 最小限の空表示 | 勝手に削除しない |

一行メモの本文を一覧の見出しへ使った場合、同じ一文をプレビューでも繰り返さないようにします。複数行なら、識別用見出しと補助抜粋を分けられます。

タイトルも、空判定と表示文字列を分けます。現在はtitle.trim()を表示に使いますが、本人の文字列を保つなら、trimは空判定だけに使う方が一貫します。

アプリが書く固定コピーの改行調整と、本人が書いた歌詞・詩・メモの表示規則も分けます。本文の空行や短い行を、自動で結合したり書き換えたりしません。本文の原文表示とwhite-space:pre-wrapは現行の良い性質なので維持します。[読み返し本文][src-read] [設計文書][src-design]

### 10.3 戻る先は、入ってきた場所から決める

| 開始地点 | 終了操作の表示 | 戻り先 | 保つもの |
|---|---|---|---|
| 一覧から新規・入力あり | 一覧へ | 新しいメモが見える一覧 | 作成したメモと保存状態 |
| 一覧から新規・未操作 | 一覧へ | 作成前の一覧 | 検索語、位置、フォーカス |
| 読み返しから編集 | 読み返しへ | 同じメモの読み返し | 可能な範囲で読んでいた位置 |
| 検索結果から読み返し | 検索結果へ | 元の検索結果 | 検索語、カード、位置 |
| 通常一覧から読み返し | 一覧へ | 元の一覧 | 対象カードと位置 |
| 削除確定 | 削除する | 元の一覧・検索 | 近傍のカードと取り消し |

現在はcreateNoteで検索語を消すため、検索中に新規を誤操作して未入力で戻っても、検索文脈を失います。前回の「未操作の空メモを残さない」は、メモを消すだけでなく、元の検索・一覧位置を戻すところまで一緒に直したい項目です。[新規作成][src-app-create]

読み返しから一文字直した時は、同じメモを読んでいた場所へ戻れると流れが自然になります。現状の編集終了は常に一覧です。[画面遷移][src-app-views]

自動保存を保ち、「保存」「完了」「読む」「一覧へ」を同時に増やしません。終了操作は行き先で名付け、保存状態を別に正確に伝えます。新規を終える全員に読み返しを強制せず、一言残して離れる用途も成立させます。

### 10.4 カードは、内容を見分けるために組む

現状のカードは日付、題名、本文の最後の非空行、全カード共通の「読み返す」という順です。[カード][src-card]

通常状態では、題名または本文冒頭を最初に、その後に短い原文、日付としるしを小さく添える案を推奨します。カード全体が操作対象であることを見た目・フォーカス・読み上げで伝えられれば、毎回同じ「読み返す」の専用行を省けます。

題名のある通常カードでは、最後の一文を残す今の表現を維持できます。検索中は一致箇所、無題では冒頭による識別、と使い分けます。

お気に入りは現状、全件を他のメモより前に並べるため、実質的に先頭固定です。[並び順][src-logic]

| 方針 | 利点 | 必要な整理 |
|---|---|---|
| 現行の先頭固定を保つ | 変更が小さく、大切なメモに戻りやすい | 印の意味を「先頭に留める」へ寄せる。新規を終えた時は新しいカードが見える位置へ |
| 印を純粋なお気に入りとして扱う | 印が増えても新しいメモを先に見られる | 時系列順と「印のあるメモ」の絞り込みを定義する |

初回の変更量を抑えるなら前者が有力です。金色を強める調整と一緒に、何を意味する操作なのかも揃えます。

## 11. 文字と余白の調整案

### 横幅は、本文を小さくする前に調整できる

現在は外側の左右21px、紙の内側にも左右21pxがあるため、本文領域は次の程度になります。紙の境界線を含めた概算です。[画面外枠][src-shell] [編集画面][src-editor] [本文文字指定][src-index]

| 画面幅 | 本文領域の概算 | 18px＋字間0.024emの全角換算 |
|---|---:|---:|
| 375px | 約289px | 約15.7字／行 |
| 390px | 約304px | 約16.5字／行 |
| 430px | 約344px | 約18.7字／行 |

全角を概ね1emとした目安で、禁則処理や個々の字形を測定した数字ではありません。

短い言葉には合う密度ですが、長い日記ではスクロール量が増えます。入力時だけ紙の内側を13px程度にすれば、375pxで本文幅は約305pxになります。本文18pxを保ち、入力時の行間1.85〜1.95、読み返し時1.95〜2.15を比較するのが具体的な調整案です。

これらは採用済みのデザイン値ではありません。かな変換、長文、文字拡大で使ってから決めます。

### 紙の装飾と、文章・操作を別の層にする

| 層 | 担当 | 設計上の注意 |
|---|---|---|
| 背景 | 月、紙の地 | 入力ごとに質感を変化させない |
| 紙の装飾 | 繊維、紙端、色ムラ | 入力や選択に必要な領域を切らない |
| 文書 | 題名、本文、カーソル、選択 | 原文と可読性を保つ |
| 操作・通知 | 戻る、保存、削除、復旧 | 装飾のクリッピングに巻き込まない |

現行の紙面本体はfilter:none!importantで、削除ダイアログもeditor-paperの外にあります。「現在のダイアログが紙のfilterに巻き込まれている」という問題は確認していません。[紙の最終補正][src-phase28] [削除ダイアログ][src-editor]

一方、clip-pathは子も含む描画を切り、filterの設定は固定要素の配置基準に影響し得ます。今後の変更では、紙の見た目を入力・通知の親全体へまとめて掛ける方法を避けると、挙動を保ちやすくなります。[W3C Masking][w3c-mask] [W3C Filter Effects][w3c-filter]

textareaを長文に合わせて自動拡張する場合、現行の紙端polygonの縦方向の割合も見直します。高さが10,000pxになると1%が100pxになるため、短い紙面用の割合を、そのまま長文全体に適用しない設計が必要です。これは将来の修正に伴う注意点で、現時点でその欠けを観測したという指摘ではありません。

## 12. コピーを、操作の意味まで揃える

| 場所 | 現行 | 推奨案 |
|---|---|---|
| 作成 | 言葉を置く／最初の余白をひらく | 同じ名称へ統一。明瞭さ優先なら「メモを書く」 |
| 題名 | この余白に名をつける | タイトル（任意） |
| 編集 | 言葉を直す | 編集する、または書き足す・直す |
| 無題 | 名のない余韻 | 一覧は本文冒頭。読み返しは大きな代替題名を置かない |
| 件数 | 11つの余韻 | 残した言葉 11件 |
| 検索ゼロ件 | その言葉は、まだ見つかっていません。 | この言葉に一致するメモはありません |
| 戻る | 戻る | 一覧へ／検索結果へ／読み返しへ |
| 保存失敗 | 保存できませんでした | 最新の変更を保存できませんでした |
| 削除確認 | この余韻を手放しますか？ | このメモを削除しますか？ |
| 端末保存 | 端末内に保存 | この端末に保存 |

現行文言の出典：[i18n.ts][src-copy]、[件数表示][src-list]。

「言葉を置く」を中心語として残す選択も十分成立します。その場合は、初回の一文で意味を伝え、以後同じ操作に同じ語を使います。全ボタンへ説明を併記して行数を増やす必要はありません。

「余白」「余韻」「しるし」は意味を固定し、保存・削除・復旧の判断には、何が起きるかを直接伝える言葉を使う方が安心して操作できます。

## 13. 実装後に使う確認用メモとシナリオ

### 共通の6種類

| メモ | 確認すること |
|---|---|
| 無題、本文1行 | 命名なしで完結し、一覧と読み返しで見分けられる |
| 長い題名＋2,000字の日記 | 題名が本文領域を潰さず、最後まで読める |
| 200字以上のURL＋日本語 | 表示がはみ出し続けず、コピーした文字列が変わらない |
| 10項目の箇条書き | 番号、空白、改行を保つ |
| 空行を含む20行の歌詞・詩 | 意図した行分けを維持する |
| 日本語、2026、3:30、英語、🌙の混在 | 回転・結合文字・抜粋で読めない箇所を作らない |

原則は、作成→保存→読み返し→途中編集→コピーまで、言葉自体が変わらないことです。内容の種類を推測して、読み途中に向きや整形を自動変更しません。縦書きで扱いづらい内容には、利用者が横書きを選べる案を検討できます。

### 日常の確認

| シナリオ | 完了条件 |
|---|---|
| 初回30秒 | 何を書く場所か分かり、本文へ1操作で入れる |
| 翌日に開く | 導入コピーより先に自分のメモへ届く |
| 検索中に新規を誤操作 | 未入力で戻ると件数・検索語・位置が元に戻る |
| 30件目を一文字編集 | 同じメモの読み返しへ戻り、一覧でも元の近くを保つ |
| 検索語を本文から削除 | 結果から外れるのは自然だが、突然先頭へ移動しない |
| 夜に一言残す | カーソルが見え、演出を待たず終了できる |
| 文字を大きくする | 操作名と文章が欠けず、スクロールして到達できる |

### 異常時の確認

| シナリオ | 完了条件 |
|---|---|
| 本体保存失敗→画面往復 | 保存失敗と再試行が消えない |
| nativeだけ失敗→本体も失敗 | 最新版に対する誤った保存済み表示が出ない |
| 未保存中に描画例外 | 最新本文を読める・コピーできる |
| 復元候補の2枠が満杯 | 候補と現在編集を守り、画面上で解決へ進める |
| 容量不足中に削除 | 削除の確定に失敗したことが分かり、本文への出口がある |
| 日本語変換中にアプリ切替 | 実機で確定文字と未確定文字の扱いを確認する |

疑似IMEの基本経路では、未確定「へんかん」から確定「変換」へ進んだ後、保存先も「変換」になりました。composition handlerが無いことだけを理由に文字消失の不具合とは報告しません。iOSキーボードのイベント順序は、上表の実機確認対象です。

また、nativeの書込み直列化は古い非同期保存が後から新版を巻き戻すことを防ぐ役割があります。全件保存やキューの存在だけを根拠に、速度の不具合とは数えていません。[native保存処理][src-native]

## 14. 修正をまとめる順番

前回の横スクロール、保存エラーの継続、復帰時の版比較、プライバシー導線という公開前の優先事項は継続します。今回の内容を合わせるなら、次のまとまりが適切です。

| 順序 | 変更のまとまり | 目に見える完成条件 |
|---|---|---|
| 1 | 保存表示と失敗時の本文保護 | いまの文章が保存済みか分かり、問題時も文章に届く |
| 2 | 縦書きの文書構造とスクロール | 冒頭から末尾まで、自然な順序で読める |
| 3 | キーボード時の編集配置 | カーソルの周囲と操作が見え、変換・選択が続けられる |
| 4 | 無題・下書き・戻り先 | 一言で成立し、元の文脈へ戻れる |
| 5 | ホーム・カード・検索の情報順序 | 自分のメモを内容で見分けられる |
| 6 | 色・紙端・日付・コピーの最終調整 | 内容と操作の優先度が、見た目にも一貫する |

保存エンジン全体や装飾全体を一度に作り直すより、それぞれの完成条件を確定してから進めると、既存の保護を保ちやすくなります。現在の保存方式でどこまで扱えるかは実機で測定し、その証拠に応じて保存基盤の変更範囲を決めます。

今回のレビューで最も重視する品質は、**自分の言葉が自然に中心へ来て、書きかけでも安心して置いておけること**です。
