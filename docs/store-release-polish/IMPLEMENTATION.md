## 5. W1 — 保存状態と復旧を一つの体験にする

主な変更箇所は [src/App.tsx](../../src/App.tsx)、[NoteEditor.tsx](../../src/components/NoteEditor.tsx)、[AppErrorBoundary.tsx](../../src/components/AppErrorBoundary.tsx)、[storage.ts](../../src/lib/storage.ts)、[nativeDurableSnapshot.ts](../../src/lib/nativeDurableSnapshot.ts)、[nativeAppLifecycle.ts](../../src/lib/nativeAppLifecycle.ts)、[saveFailureUi.ts](../../src/lib/saveFailureUi.ts)、[i18n.ts](../../src/lib/i18n.ts) である。ファイル分割は必要な境界に限定し、全保存基盤の書換えと見た目の整理を同時に行わない。

### 5.1 表示中の版・本体に保存した版・nativeに保存した版を区別する

保存の事実と、短時間の成功演出を別の状態として扱う。具体的な型名や分割方法は実装担当に委ねるが、次の情報関係を失わない。

| 情報 | 意味 | 使用上の制約 |
|---|---|---|
| 表示中の編集版 | 最後にアプリが受け取った現在のメモ集合と、その変更を識別する値 | 作成・削除・印の変更も集合の変更として追跡する |
| 本体への確定版 | 本体への書込み成功を確認した内容、または本体に現存する内容との一致を確認して明示採用した版 | native候補や未保存候補を選択しただけでは本体に保存済みとしない。別の新しい編集に対する成功へ読み替えない |
| nativeへの確定版 | native書込みが成功した内容 | 本体の成功だけでnative成功とはしない |
| 保存操作の識別 | 書込み対象の版、操作ID、writer、必要な世代番号 | 遅れて返った結果が何に対するものか確認できる |
| 比較操作の世代 | 起動・復帰・再試行で実行した安全確認の世代 | 古い比較結果で新しい候補を置換しない |

変更番号は自分の実行中の処理を対応付けるために使う。端末内の別候補の正しさを推測する時計として使わず、`updatedAt` の大小だけで正本を選ばない。新しい永続スキーマを導入しなくても成立する案を先に検討する。

最低限の状態契約は次のとおり。

- エディタを開き直しても、未保存・保存失敗・競合は消えない。
- 最新の編集が未保存なら、過去の成功結果で「保存済み」にしない。
- 過去のnative失敗を、最新版本体の保存失敗より強く表示しない。
- 最新版の本体保存が失敗している時に、「メモ本体は保存されています」と無条件に伝えない。
- 保存が成功した場合でも、結果が戻る前に次の編集が始まっていれば、その次の編集は未保存として残す。
- 画面移動や演出タイマーの終了を、失敗解消の条件にしない。
- 利用者が未保存編集を明示的に破棄し、別の保存済み版を採用した場合は、その確定した事実に合わせて表示を更新する。
- 同じ内容に戻った時は既存のno-op成功を維持する。不要な書込みで容量不足を起こさない。

### 5.2 利用者に見せる保存表示を統一する

| 状態 | 主表示 | 必要な操作 |
|---|---|---|
| 最新版を保存中 | 保存中 | 通常操作を続けられる。演出を待たせない |
| 最新版本体の保存失敗 | 最新の変更を保存できませんでした | 再試行、未保存内容の取り出し |
| 版が競合して停止 | 内容を確認するため、保存を止めています | 候補の確認と明示選択 |
| 安全確認中 | 保存内容を確認しています | 関連操作にもbusy/disabledを反映 |
| 読込み安全確認の失敗 | 保存内容の安全確認ができませんでした | もう一度確認する。存在しないものとして進めない |
| 最新版本体は成功、予備保存だけ失敗 | 最新の変更は保存済みです。端末内の予備保存を更新できませんでした。 | 予備保存の再試行 |
| 最新版の必要な保存が成功 | 保存済み | 短く表示して通常状態へ戻す |

実際の文言はDESIGNに揃える。内部のstorageキー名や世代番号を通常画面へ露出させる必要はない。

R07のエラー色はこの段階で直す。成功用の薄い文字色を失敗へ継承させず、読み取れる文字サイズとコントラスト、未保存の意味、次の操作を確保する。色だけに依存しない。

安全確認で作成・編集を一時停止するなら、押せる・入力できるように見せてから無反応にしたり、受け取ったように見える入力を元へ戻したりしない。停止開始前の内容とキャレット位置は保つ。通常の保存中まで入力禁止にしない。

### 5.3 起動と復帰の全入口で、同じ整合性の原則を使う

対象入口は、起動、`pageshow`、`visibilitychange`での再表示、Capacitorのactive復帰、関連するstorage変更、復旧の再試行である。少なくとも監査で問題になった復帰3入口を、本番のイベント接続から検証する。

1. dirty編集、保存guard、比較中の世代、既に提示した候補を把握する。
2. 既知の正本と異なるlocal保存版を見つけても、形式が正常という理由だけで採用しない。
3. native環境では必要な比較を完了させるまで、異なる版でnativeを上書きしない。
4. localとnativeが同じ、またはnativeの不存在を正常に確認できた場合は、既存の起動方針に沿って通常利用へ戻す。
5. 異なる有効版なら、現在の未保存編集・local候補・native候補を独立して保持する。
6. 読込み失敗と不存在を分ける。上位世代が読めない時に古い世代を正しい版と断定しない。
7. 比較の途中で入力、保存先、候補、再試行が変わった場合は、操作の世代を確認する。古い結果は採用せず、必要なら新しい比較へつなぐ。
8. 比較し直す必要が生じても、永遠に「確認中」に残さない。再確認可能な失敗状態へ到達できるようにする。

未保存編集は比較前・比較中・候補切替中を通じて保持する。一度提示した候補への編集を、その後の非同期読込みで置換しない。`[]` を含む候補は明示的な状態で区別し、`length > 0` だけで候補の存在を判定しない。

既存の完成済みjournalの整合回復と、未選択の別版を自動採用することを混同しない。既存の保存回帰を維持した上で、どの経路で正本が確定するかをレビュー可能にする。

### 5.4 比較できる復元画面を作る

長い説明と全ボタンを画面上端の固定バナーへ詰め込まない。通常画面には短い保存停止の案内を残し、内容を確認する専用画面またはスクロール可能な領域へ進める。

- 候補ごとに、件数、利用者の題名または本文による識別、内容の見本を表示する。
- 更新日時を判断材料として示す場合も、それだけで新旧や正しさを断定しない。
- 0件の候補は「すべて削除した内容」であることが分かるようにする。
- 同じタイトル・同じ件数の候補でも、違う本文を全文確認できる。
- 「この内容を残す」を選ぶまで、他の候補を自動で混ぜたり破棄したりしない。
- 小画面・文字拡大でも、本文の確認、候補の切替、確定、取りやめへ到達できる。
- フォーカス、読み上げ順序、確認を閉じた後の戻り先を定める。

### 5.5 描画エラーの外に、最後の下書きへ届く経路を残す

AppErrorBoundaryがAppを破棄しても、最後に受け取った未保存文章を参照できる構造にする。下書きの保持または保存制御を、表示エラーで失われる境界の外に置く案を優先する。

エラー画面に最低限必要なものは次のとおり。

- 最後に受け取った未保存の題名・本文を、読み取り専用で確認する方法。
- 文字列を選択・コピーできる方法。Clipboard APIが使えない場合も手動選択へ進める。
- どこまで保存済みか、分かる範囲を正確に示す案内。
- 再読み込み前に未保存内容を取り出せる順序。

保存済みの正本、未保存の下書き、復元候補を同じ箱へ上書きしない。描画エラー後の保存を行う場合も通常の競合保護を通す。一律のunmount時force-saveは禁止する。

コピー・書出しが成功した事実と、アプリ本体への保存が成功した事実は分ける。取り出せたことを理由に未保存状態を解除したり、「保存済み」と表示したりしない。

受入は、正常な保存待ち・容量不足で失敗中・競合待ちのそれぞれで、実際のBoundaryへ描画例外を注入して行う。エラー後に5秒待ったことだけで合格にせず、利用者が文章を取り出せることと、既存版を上書きしていないことを確かめる。

### 5.6 保護候補が満杯の時、保存完了へ進める導線を作る

現在の `storage.ts` は、recovery archiveの2枠に異なる正常候補があると、第三の候補を失わないため保存を止める。この保護は維持する。

通常の版競合と区別できる結果を追加する。名称は例えば `recovery_archive_full` とし、UI、型、テスト、既存の結果を扱う全箇所で意味を統一する。一般的な「もう一度保存する」を同条件で繰り返させない。

解決の流れは、以下の順で成立させる。

1. 現在の未保存編集と全ての未確認候補を保持する。
2. 保護中の候補を、内容で確認できるようにする。
3. 必要な候補を取り出せるようにする。対象が1メモか候補全体かを明確にする。
4. 利用者が確認した候補について、何を整理するかを具体的に示して明示選択を受ける。
5. その選択の間に候補が変わっていないことを再確認して、選ばれた対象だけを整理する。
6. 現在の内容を保存し直し、成功を実際の結果で確認する。

候補の自動削除、最も古そうな候補の自動破棄、説明なしの上書きは禁止する。取り出しを伴う場合は、生成・コピーの失敗を成功扱いしない。ファイルを出す設計を採用するなら、内容の原文一致と対象範囲を検査する。

これは復旧を完了するための最小限の取り出し機能である。通常時の多形式バックアップ管理、クラウドへの送信、全面的な履歴機能を同時に追加する必要はない。ただし、「満杯です」という説明だけを付けて未完了としない。

### 5.7 容量不足は、削除すれば解決すると案内しない

第2回の合成計測では、通常更新中のlocalStorageの値文字列長が、スナップショット長Sの約4.02倍まで増え、保存完了後は約2倍となった。旧版と新版を含むjournalを書いてから復旧コピーと本体を更新するためである。

この値はUTF-16コード単位による合成データの結果であり、iPhoneの空き容量、使用バイト数、保存可能件数を表さない。エスケープ文字や保護候補によっても変わる。4.02を全データ共通の定数として容量制限へ組み込まない。

最終的にデータが減る削除でも、途中のjournal書込みで容量不足になり得る。次を必須にする。

- 容量不足を「不要メモを削除してください」だけで解決させない。
- 保存できていない現在の内容を取り出せる。
- 既に保存した内容と現在の編集を区別し、元に戻す場合は対象が分かる。
- 同じ内容へ戻ったno-opは、追加書込みなしで成功できる既存の性質を保つ。
- journal書込み、復旧コピー書込み、本体書込み、後片付けの失敗を区別して検証する。
- 本体保存に失敗した今回の版が、自動でnativeへ代替保存されると仮定しない。

nativeには以前から投入済みの書込みが残る場合がある。新しい本体保存の失敗と、それらの完了結果を混同しない。

保存方式を1メモ単位やトランザクションのある方式へ変える場合は、実測による必要性、既存キーからの移行、途中中断、ロールバック、破損復旧、異なる旧版との共存を別の検証対象にする。journalやバックアップだけを削って容量を減らす変更、根拠のない全面移行を今回の小修正へ混ぜない。

### 5.8 nativeキューとIMEについて、確認済みの性質を壊さない

native書込みのPromise chainは、古い書込みが後から新版を巻き戻すことを防ぐ保護機能である。UIの遅延を消すために並列書込みへ変えない。キューを変更する必要がある場合は、順序、失敗後の再試行、最新内容、読込み前の整合を検証する。

監査では疑似IMEの開始→仮文字→確定→最終input→保存という経路は正常だった。composition handlerがないことだけを不具合として修正しない。実機の変換候補選択、アプリ切替、画面ロックを通し、問題のあるイベント順序を確認してから対処する。

### W1の出口

保存事実が画面遷移と非同期処理を越えて一貫し、比較前の自動上書きがない。失敗・描画例外・候補満杯・容量不足から、文章を失わず次の操作へ進める。既存の保存回帰と追加の望ましい挙動のテストが成立する。実機の確認はACCEPTANCEに状態を分けて残す。

## 6. W2 — CSS・縦書き・可読性の基盤を整える

主な変更箇所は、`src/main.tsx`、`src/index.css`、`src/phase*.css`、`tailwind.config.js`、AppShell・ReadMode・NoteEditor・NoteCard・SaveAfterglow・ZanshinDateStampである。

### 6.1 上書きの原因を減らす

- CSSをトークン、背景・紙装飾、文書、操作、状態表示の責務に整理する。
- 新しいphaseファイルを末尾へ足して勝たせる修正を繰り返さない。
- 特に `overflow`、`position`、`writing-mode`、`display`、文字色、透明度、focusの定義元を明確にする。
- `.editor-paper > *` のような広い指定で、保存演出や操作の配置まで変えない。
- 先に必要な構造と生成CSSを確かめ、整理後に不要となった重複を削る。過去ファイルをまとめて消してから見た目を作り直す進め方は避ける。

R27の設計文書整理もここで行い、READMEから現在の初版方針と手順へ一意に辿れるようにする。監査の証拠文書は履歴として保ち、実装済みの現在仕様と分ける。

### 6.2 紙の装飾と操作面を分ける

紙端のclip-path・繊維・色ムラは、本文スクロール、キャレット、選択、focus、通知を切り取らない層へ置く。固定操作・ダイアログを、将来filterやclip-pathを掛ける装飾の親へ入れない。

SaveAfterglowは装飾として通常フローから外す。非表示時・保存中・成功時で本文の開始位置や読書領域の高さが変わらないことを確認する。

現行コードで「ダイアログが紙のfilterに巻き込まれている」とは確認されていない。未発生の問題を実測済みとして報告せず、変更後も安全な構造を維持するための条件として扱う。

### 6.3 縦書きの文書と横スクロールを一つの構造にする

1. 操作バーは横書きで独立させる。
2. 日付は本文の縦方向の行長を圧迫しない情報領域へ置く。
3. タイトルと本文を右から左へ流れる文書として配置する。
4. 横スクロールを所有する領域を一つにする。
5. 初版は連続スクロールを基本とし、実際のページ分割をしないままタイトルと本文だけへsnapを付けない。
6. 続きが領域外にある時だけ、読み進める案内を表示する。

`vertical-rl` の `flex-direction:row` は物理的な横並びではない。inline/blockとx/yの軸を設計し、区切り線の `margin-inline` やスクロール連鎖の指定を意図した方向へ揃える。`overflow-x:auto` を書き足すだけでR31を完了にしない。

右端の冒頭から左端の末尾へ、タッチ・適切なキーボード操作で到達できることを確認する。`scrollLeft` の符号などエンジン差へ依存した処理を採用する場合は、対象WebViewで検証する。プログラムで位置を動かせたことを、指で全文を読める証拠にしない。

日本語の縦書きを主役に保つ。横書きの読み返しは、英語・URL・混在文や文字拡大で実用上の問題が残ることを確認し、DESIGNの条件に沿って導入する。自動言語判定で原文や本人の選択を勝手に変更しない。

### 6.4 文字の役割と生成結果を揃える

- 入力本文18px前後の読み心地を起点に、DESIGNの役割別トークンで整える。
- 操作、保存状態、日付、件数を、小ささと薄さの両方で弱めない。
- Tailwindの未生成クラスは有効な指定またはトークンへ置き換える。誤って無効だった低い透明度を、そのまま有効化して見えにくくしない。
- 文字色のalphaと祖先のopacityを重ねて管理しない。読ませる文字の濃さは把握できる場所で決める。
- 通常文字4.5:1を設計目標に、紙との合成後の色を確認する。基底色だけの計算値と実際のテクスチャ上の測定を区別する。
- タイトルは編集時に自然に折り返し、一覧では概要を保ち、読み返しでは全文へ届く。表示の省略を保存データへ反映しない。
- タイトル200文字、長い英数字、URL、絵文字、空行を共通データで確認する。

pxからremへ変えただけでDynamic Type対応済みとしない。OS設定への追従またはDESIGNの文字サイズ経路を実装し、標準・大きめ・200%相当で全画面を通す。文字を縮めてボタンを押し込まず、縦積みやスクロールへ切り替える。

### W2の出口

生成CSSと実画面で、横スクロール、演出の配置、色、文字拡大、focus、長いタイトルが成立する。短文と長文で同じ構造を使え、装飾を変更しても文章・操作の領域が破綻しない。

## 7. W3 — 書く・探す・戻るを整える

### 7.1 ホームの3状態と新規作成

空・通常・検索の3状態をDESIGNに沿って整理する。通常状態では自分のメモへ早く届き、空状態では最初の操作と端末内自動保存が分かるようにする。作成ボタンの基本位置をメモ数で大きく移動させない。

新規作成の名称は、空状態も常設操作も「メモを書く」に統一する。長い操作説明を全ボタンへ併記しない。

新規の未操作下書きは、戻っただけで一覧へ確定しない。次を別扱いにする。

- 一切操作していない新規下書き。
- 題名または本文を書いた新規メモ。
- 題名だけのメモ。
- 利用者が意図して空にした既存メモ。

最後の2つを、空に見えるという理由で自動削除しない。未操作下書きの判定に、全メモ共通の `trim()===""` だけを使わない。入力中の未確定文字も見落とさない。

### 7.2 題名任意を全画面へ通す

題名の入力案内は「タイトル（任意）」とする。

| 内容 | 一覧 | 読み返し |
|---|---|---|
| 題名あり | 本人の題名 | 本人の題名を全文読める |
| 題名なし・本文あり | 本文の最初の非空行を識別用見出しにする | 大きな架空の題名を加えず本文から読む |
| 題名のみ | 本人の題名 | 本文を要求しない |
| 既存メモを本人が空にした | 他の空メモと区別できる最小表示 | 最小限の空表示を使う |

代替見出しを実際のtitleへ保存しない。trimは空判定に使い、表示・保存の都合で本人の原文を不要に削らない。無題の一行メモを、見出しと抜粋で同じ内容を二度表示しない。

### 7.3 検索結果には、一致した理由を見せる

通常一覧では題名のあるメモの最後の一文という表現を保てる。検索中は、一致箇所を含む短い抜粋を優先する。本文冒頭・中間・末尾のどこで一致しても、結果を開く前に理由が分かるようにする。

- 検索語をカードへ渡すなど、通常表示と検索表示の契約を明確にする。
- 元本文を加工して保存しない。
- 見た目の一文字のまとまりを壊さず、絵文字・結合文字を切らない。
- 検索解除後は入力欄へフォーカスを戻し、続けて入力できるようにする。
- 件数は「残した言葉 11件」など自然な表記へ統一する。
- ゼロ件は、条件に一致するメモがないことを明確にする。保存データが消えたようには伝えない。
- 結果件数の読み上げは入力を妨げない頻度にまとめる。

曖昧検索・AI検索・複雑なタグを今回追加する必要はない。正規化を拡張する場合は、検索のための変換と原文の範囲対応を検証し、抜粋の位置をずらさない。

### 7.4 戻る先は、来た場所から決める

| 入口 | 終了操作 | 戻る先と保持するもの |
|---|---|---|
| 一覧・検索から新規、未操作 | 一覧へ／検索結果へ | 作成前の検索語、位置、focus |
| 一覧から新規、入力あり | 一覧へ | 新しく作成したメモが見える位置、保存状態 |
| 読み返しから編集 | 読み返しへ | 同じメモ、可能な範囲の読書位置 |
| 検索結果から読み返し | 検索結果へ | 元の検索語、対象カード、位置 |
| 通常一覧から読み返し | 一覧へ | 対象カードと位置 |
| 削除を確定 | 削除する | 元の一覧または検索、近傍カード、取り消し |

画面種別とIDだけでなく、必要最小限の入口情報・検索語・対象カード・スクロール位置を保持する。配列のindexだけを戻り先にせず、編集や印による並び替え後も対象を見つけられるようにする。

新規を開いた時点で検索文脈を不可逆に捨てない。入力ありの新規を終えた時は、印付きメモの後ろに新規が並んでも、その新しいカードへ届くようにする。

保存・完了・読む・一覧へを同時に増やさず、終了操作は行き先で伝える。保存状態はW1の事実表示として独立させる。

### 7.5 印、日付、削除、読み上げ

#### R20・R22：初版は既存の変更日時と並びを維持する

金のしるしは「大切なメモを先頭に留める」意味として短く説明する。色だけで状態を区別しない。並びは印ありを先頭とし、各グループ内は**変更の新しい順**とする。印の切替も変更に含むことを、並びの案内と必要な読み上げに反映する。

初版は新しい日時フィールドを追加せず、以下を採用する。

| 項目 | 実装・表示の契約 |
|---|---|
| `createdAt` | 作成日時として不変。カード・編集・読み返しの日付印は引き続きこの値を使い、「作成日」と分かるようにする |
| `updatedAt` | 題名・本文・印を含むレコードの変更日時。現行どおり印の切替でも更新し、その変更を保存する |
| 並び順 | 印ありを先頭へ、同じグループ内は `updatedAt` の新しい順。印の解除で戻る位置も、この変更順に従う |
| 日付の呼び方 | `updatedAt` を表示・説明するときは「変更日」とする。「本文の最終編集日」と呼ばず、作成日と変更順の違いを短く伝える |

この案を選ぶ理由は、[App.tsx](../../src/App.tsx) の `updateNote` がすべてのpatchで `updatedAt` を更新し、[notesLogic.ts](../../src/lib/notesLogic.ts) の並びだけでなく、[storage.ts](../../src/lib/storage.ts) の重複IDの復元候補選択と `mergeRecoveredNotes` もこの値を使っているためである。印変更時の日時だけを止めると、表示の調整を超えて復旧の前提を変えてしまう。今回は表示・説明を実際の変更順に合わせ、既存の保存形式と復旧互換を保つ。

`updatedAt` を強い版番号として扱わない。W1の候補比較では日時だけで正本を選ばず、印や未知の将来フィールドを含む構造の違いを引き続き検知する。表示用オブジェクトを保存データへ作り直して未知フィールドを落としたり、既存のmerge・競合・journal・no-opの回帰を弱めたりしない。

R22の受入では、題名変更・本文変更・印を付ける・印を外す操作を通して、変更日時と並び、作成日、保存結果を照合する。保存後の再読込みでも印が残り、既存の復旧経路で新しい印の変更が古い候補へ戻らず、未知フィールドだけの差分も競合として検知されることを確認する。同時刻の異なる候補が存在し得ることは引き続きW1の保全対象とし、日時が等しいだけで同一内容と判定しない。**R22の完了条件は、表示・並びの意味が実際の保存内容と一致し、保存・復旧の保護が維持されることである。**

本文・題名だけの編集順を将来必要とする場合は、`contentUpdatedAt?` のような任意フィールドを別の計画で検討する。導入時もレコード変更用の `updatedAt` を維持し、旧版との往復、未知フィールドの保全、移行・復旧の回帰を検証する。既存メモの真の本文編集時刻は分からないため、過去の値を捏造しない。旧データの並びには `updatedAt` をfallbackとして使えても、それを正確な本文編集日時として表示しない。このフィールド追加は今回の実装範囲に含めない。

#### 削除と読み上げ

- R37の作成地の記録・既存データ移行はこの段階で実装しない。過去の作成地を現在地から推測しない。
- 削除確認のfocus循環とキャンセル時の復帰を維持する。小画面・文字拡大では説明と両操作へ到達できる配置にする。
- 取り消しの10秒・直前1件・現在の起動中という現行条件を説明と照合する。猶予を変更する場合は理由と新条件を記録し、無断で大きなゴミ箱機能へ広げない。
- 無題カードでも、本文冒頭・日付・印の状態から読み上げで識別できるようにする。
- 保存の通常成功通知を短い入力ごとに繰り返して執筆を妨げない。失敗と競合は確実に伝える。
- 新画面の見出し、元カードへのfocus復帰、ロゴと見出しの重複読み上げを確認する。

### 7.6 キーボード表示中の本文領域を優先する

閉じている時と入力中で、日付、題名、紙の内側の余白、保存表示を調整する。本文を小さくする前に、本文より前に積まれる装飾・余白・空の題名領域を見直す。

- 入力中にtextareaのDOMを差し替えず、日本語変換と選択範囲を保つ。
- 操作バーと編集領域の関係を明確にし、キーボードの後ろへ戻る操作を取り残さない。
- 全体スクロールとtextarea内部スクロールを不用意に競合させない。方式は長文と選択操作を含めて決める。
- `dvh` だけでキーボードに追従したと判断しない。実WebViewの挙動を見て、必要な時だけviewport処理やKeyboard連携を選ぶ。
- 通常文字サイズで本文4〜6行程度を見通せることを調整目標にする。文字拡大時まで同じ行数を保証するために文字を縮めない。
- textareaを内容高へ伸ばす案を採用するなら、長文の再計算負荷、キャレット、選択ハンドル、紙端の割合指定を見直す。

監査の約304pxという本文開始位置や、仮定したキーボード高は、CSS指定からの概算である。実機の見え方として引用せず、調整後の測定と置き換える。

### W3の出口

初回でも作成方法が分かり、題名なしで書ける。探した結果を識別でき、元の場所へ戻れ、印・日付・削除の意味が一致する。キーボードと読み上げを含む日常の流れを、ACCEPTANCEの共通メモで確認する。

ストア画像は、紙の雰囲気だけでなく「横書きで書く」「縦書きで読み返す」「残した言葉を探す」「この端末に保存する」が分かる構成にする。修正前の画面や、未実装の機能を完成品として使わない。

最新のApple公式要件を実提出時に確認し、使用Xcode・SDK、最低対応OS、アプリ版、コミット、Archive結果を記録する。2026年11月26日の監査で確認した提出SDK要件と、アプリの最低対応OSを同じ意味として扱わない。

Release Archive、実機、TestFlight、提出物は同じコミットとビルドに結び付ける。Linuxでのbuildや `cap sync ios` を、Xcodeビルド・署名・実機・TestFlightの代替証拠にしない。

### W4の出口

アプリ内の案内、公開ページの内容、対応言語、プライバシー説明、ストア画像計画、提出文面が現在の初版に合っている。本人設定や外部操作が残る場合は、対象と具体的な残件が分かる。

## 9. W5 — 統合確認と引き渡し

### 9.1 同じ変更一式で確認する

個別テストだけでなく、W1〜W4をまとめた対象コミットで、次の一連の体験を確認する。

1. 機内モードで起動し、空状態から題名なしの一文を書く。
2. 一覧へ戻り、メモが保存され、他の無題メモと識別できる。
3. 長文を開き、縦書きの最後まで読み、途中を編集し、元の読書位置へ戻る。
4. 本文中間の語を検索し、一致部分から選び、検索結果へ戻る。
5. 印を切り替え、保存・復旧結果と並びが「メモ全体の変更日時」という説明に一致し、作成日は変わらないことを確かめる。
6. 保存失敗を作り、画面を往復しても未保存状態と救済手段が残る。
7. 復帰時の別版・読み取り失敗・0件候補・三候補を、安全に確認して選ぶ。
8. 描画例外、保護候補満杯、途中書込みの容量不足でも、文章を取り出し解決へ進む。
9. 削除と取り消しを行い、説明された範囲で元に戻せる。
10. 「このアプリについて」からポリシーを開いて、元の状態へ戻る。

データ、文字倍率、端末幅、キーボード、VoiceOver、動きを減らす設定の組合せと証拠は、ACCEPTANCEの表を使う。新しい検証台帳を別に増やして状態を分散させない。

### 9.2 自動検証と環境制約

現在のpackage scriptsとNode要件を確認してから、通常の型検査・lint・テスト・buildを実行する。保存やイベント接続を変更した箇所は、対応する既存回帰と追加の望ましい挙動を確認する。

`npm run check` が環境理由で止まった場合は、次を分けて報告する。

| 区分 | 記録すること |
|---|---|
| 通常コマンド | コマンド、対象コミット、成否、実際に止まった段階 |
| 代替検証 | 一時設定の差分、除いた要素、実行した範囲と件数 |
| 本番ビルド | 通常設定での成否、生成CSSと成果物の確認 |
| native同期 | `cap sync ios` の成否、生成差分、環境警告 |
| Xcode・実機 | 実施環境と同一ビルドの証拠、または未実施という状態 |

一時設定は実装の正しさを確かめるために使い、環境エラーを解決した証拠にはしない。検証用の合成メモ、障害注入、debug表示、暫定URLを本番へ残さない。

### 9.3 完了報告に含めるもの

- 対象ブランチ・コミットと、完了したR番号。
- 各段階で変わった利用者の体験と、その理由。
- 通常コマンド、代替検証、実画面、実機を区別した結果。
- 保存モデル・既存データへの影響と、移行がある場合の証拠。
- 残っている実機項目、本人設定、外部操作。実施済みと混ぜない。
- R37など初版に入れなかった項目と理由。
- mainへのマージ、公開、アップロード、配信について、実際に行った操作だけを記載する。

R番号を消して「全体をきれいにした」とまとめず、ACCEPTANCEから各修正の根拠と確認結果へ辿れる状態で引き渡す。

## 10. 実装中の判断基準

迷う変更では、次を順に確認する。

1. 利用者が書いた文章、保存状態、元の位置のいずれかを失わないか。
2. 小画面・文字拡大・キーボード・読み上げでも、次の操作が分かるか。
3. 既存の安全性を保ったまま、今回確認した条件を解決できるか。
4. 調査上の仮説を、未検証のまま実装済みの事実として扱っていないか。
5. 同じ目的を、より小さくレビューできる変更で達成できないか。

通常の細部はDESIGNとこの基準に沿って進める。本人の選択が必要な新しい製品範囲や外部操作に達した時だけ、完成した差分・候補・検証結果を示して確認する。既に依頼された実装の途中で、必要な準備まで止めない。
